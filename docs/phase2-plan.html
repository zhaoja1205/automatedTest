◆ 第二阶段目标

保持规则引擎作为基线，在结果判定和失败分析两个环节引入 AI 能力，形成"规则 + AI"协作模式。

核心定位

第一阶段的规则引擎在以下场景存在局限——第二阶段通过 AI 补齐：

场景规则引擎局限AI 补齐方式
语义模糊的预期结果 关键字匹配无法理解"帧率稳定""无异常"的语义 AI 语义级 Pass/Fail 判定
可忽略的 warning 误判 error 关键字检测无法区分致命和可忽略 AI 上下文理解，区分严重等级
失败根因定位 只输出"匹配率 60%"，用户需逐行看日志 AI 自动分析根因 + 给出证据行和修复建议
结果报告 仅 Excel 回写状态，无汇总分析 AI 生成结构化测试报告

判定级联架构

步骤解析(规则) → 执行 → 结果判定(规则) ──┬── confidence ≥ 0.8 → 直接采用 │ └── confidence < 0.8 → AI 语义判定 │ ├── confidence ≥ 0.7 → 采用 AI 结果 └── confidence < 0.7 → NEED_REVIEW 执行完成 → Fail 用例 → AI 失败分析 → 根因 + 证据 + 建议 执行完成 → 全量结果 → AI 报告生成 → Markdown / Excel / 文本

⊘ 失败根因分类体系

AI 分析输出的五类根因标准，用于失败用例的自动归类。

类别标识典型特征前端颜色
环境问题 environment SSH 断连、Init failed、timeout、设备未就绪、残留进程占用 amber
真实缺陷 defect 功能异常输出、崩溃、返回值错误、帧率异常偏低 red
用例问题 test_issue 命令不存在、预期过严、步骤遗漏、超时值不足 purple
间歇性 flaky 历史时通时不通、竞态、timing 敏感、温漂 blue
判定不匹配 mismatch 执行成功但阈值过严、格式变化、无关 warning 误判 grey

$ 降本与降级策略

策略说明
按需触发默认手动点击才调用 AI，不自动对所有用例分析
日志截断只发送最后 2000 字符 + 错误行上下文 5 行，减少 token 消耗
结果缓存同一 case_id + 同一 error_msg 缓存 24h，重复查看不重新调用
模型分层判定默认 Haiku（便宜快速），复杂分析可切 Sonnet（更准确）
离线降级无 API Key 或网络不通时，自动降级到纯规则模式，UI 正常使用
本地模型支持 Ollama + 开源模型（Qwen2.5 等），离线环境零 API 费用
Token 消耗估算：单次失败分析约 2K input + 500 output tokens，使用 Haiku 4.5 约 ¥0.003/次。50 个用例全部 Fail 的极端情况下，单次执行 AI 费用 < ¥0.2。
